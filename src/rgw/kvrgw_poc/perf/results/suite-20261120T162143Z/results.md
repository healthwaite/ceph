# KVRGW FDB Perf tests results

Performance benchmarks for kvrgw on a 5 node FoundationDB cluster.
The following tests were run:

- 01-run-put-object: reports/01-run-put-object.txt
- 02-run-list-single: reports/02-run-list-objects-single-thread.txt
- 03-run-list-objects: reports/03-run-list-objects.txt
- 04-run-overwrite: reports/04-run-put-object-overwrite.txt
- 05-run-versioned: reports/05-run-put-object-overwrite-versioned.txt
- 06-run-delete-multi: reports/06-run-delete-multi.txt

## Cluster setup

### Nodes

The cluster has 6 identical bare-metal nodes. FoundationDB runs on host1-host5. The
perf workers run on a seperate node.

| Resource   | Per node                                    |
|------------|---------------------------------------------|
| RAM        | 256 GiB                                     |
| CPU        | 1 x AMD EPYC 7713, 64 cores, SMT disabled   |
| Data disks | 20 x Intel SSDPF2NV153TZ NVMe, 15.36 TB     |
| Filesystem | ext4 (noatime, nodelalloc), /disk1../disk20 |

### FDB cluster

FDB is deployed with redundancy mode `triple`. We have coordinators on 5 nodes.
We have 18 storage processes per node. Each storage process has it's own disk.
Each log process has its own disk.

## Object naming format

Objects are spread over 10 buckets named `rgwkv-0` to `rgwkv-9`. The key space is
generated by the harness, so no key list is stored: every key can be rebuilt from
a few integers. All tests use `padding_bytes = 200`.

The random part of a key is drawn from a 70-character set: `0-9`, `a-z`, `A-Z`
and `! - _ . * ' ( )` (no `/`).

When keys are initially inserted during the `load` benchmark they take the
following form:

```
<random prefix: 200 chars><id: 20 decimal digits, zero padded>
```

This gives a total size fo 220 bytes. `id` runs from 0 to 1 billion - 1.  The
random prefix is seeded with the id, so the key for an id never changes.  The
ids are split into 10 contiguous blocks: bucket `b` holds ids `b * 100M` to `(b
+ 1) * 100M - 1`.  The key order in a bucket is therefore not the id order the
prefix is random.

For readability, the examples below use `padding_bytes = 8` instead of 200:

```
id 0           ->  .O94BuHu00000000000000000000
id 123456789   ->  Lg5VxSuA00000000000123456789
```

The `run-put-object` test writes **new** keys - i.e. it does not overwrite
existing keys. We use a different syntax for these keys to ensure that
every invocation of `run-put-object` always writes new keys and the new
keys can be explicitly checked for.

```
<random prefix: 200 chars><start time: 8 hex><thread id: 4 hex><counter: 20 decimal digits>
```

This gives a slightly largeer size of 232 bytes. The length is how the verifier tells the two kinds apart.

`start time` is the Unix time in seconds at which the run started, so the keys
of different runs never collide.

`thread id` is the global thread number, `worker_index * threads_per_worker +
thread_index` (0 to 4095 with 32 workers x 128 threads). A thread writes into
bucket `thread id % 10`.

`counter` starts at 0 for each thread and goes up by one for every
successful put. The keys of one thread are therefore `counter = 0, 1, 2, ...`
with no gaps.

The random prefix is seeded from a hash of (start time, thread id, counter), so
the new keys are spread over the whole key range just like the loaded ones.

Examples (`padding_bytes = 8`, start time `0x6b008d37`, thread id 17):
```
counter 0  ->  X91k9NBi6b008d37001100000000000000000000
counter 1  ->  5m-Su0ge6b008d37001100000000000000000001
```

Only keys of the format above are written by `run-put-object`. The overwrite
and delete tests work only on the loaded keys and never touch these new keys.

## What is measured

Each test writes its own results directory, and `kvrgw-perf report` turns it into
a text report. Everything is sampled over the whole run; the report skips a
warmup period and gives per-window statistics (min, max, avg, median, p90, p95,
p99 and deviation across windows).

- **Client:** calls, errors, ops/s and latency (mean, p50, p90, p99, p99.9, max)
  per operation, keys listed/deleted per second, errors by code, and the
  verification result. Latencies are measured around the call into the service
  layer, so they include FoundationDB round trips but no S3/HTTP front end.
- **Worker CPU:** cores used by the workers and by the whole host, and ops/s per
  core.
- **FoundationDB:** transactions, reads, writes and conflicts per second, storage
  and log queues, durability lag, and per-process CPU, memory and disk activity.
  The report sums CPU by role, shows how evenly storage CPU is spread and flags a
  hot storage process. It also gives the disk space used by FDB at the start and
  end of each test and the cluster configuration at the start.
- **Library:** batch queue, transaction retries and failures, and errors.

We used a 1 hour warmup and 10 minute windows for the 12 hour tests and the delete
test, and a 2 minute warmup and 2 minute windows for the list tests.

## The benchmarks

We run the following suite of benchmarks in order.

### Test0: Load 1 billion (00-load)

We use 32 workers each with 128 threads. Keys are split evenly across the 32 x
128 threads.

1. Create 10 buckets (with versioning disabled)
2. Load up 1 billion keys evenly across the 10 buckets
3. Verify: list all objects and check every one is accounted for

## Test1: PutObject (01-run-put-object)

We use 32 workers each with 128 threads. The benchmark runs for 12 hours.
Each thread continually writes new keys (i.e. does not overwrite).

Verification: we use ListObjects to ensure all newly written keys are present.

## Test2: ListObjects single worker single thread (02-run-list-objects-single-thread)

We use a single worker with a single thread. The worker picks the first bucket
(rgwkv-0) and lists the objects in the bucket using a page size of 1000. The
test runs for 20 minutes. If the thread reaches the end of the range it goes
back to the start.

Verification: at the end of the test we do a final ListObjects verification
to ensure that all initially loaded 1 billion keys are present.

## Test3: ListObjects multi thread (03-run-list-objects)

We use 10 workers each with 16 threads. Each worker looks at a single bucket.
e.g. worker-0 -> bucket-0, worker1 -> worker1... We then split the key range
up into single character prefixes (70 in total for our character set) and
distribute the prefixes over our 16 threads. Each thread scans all object
keys in its prefix lists using a page size of 1000. When a thread gets to
the end of its prefix list it goes back to the start. We run the test for 20 minutes.

Verification: at the end of the test we do a final ListObjects verification
to ensure that all initially loaded 1 billion keys are present.

## Test4: PutObject Overwrite (04-run-put-object-overwrite)

We use 32 workers each with 128 threads. The benchmark runs for 12 hours.
We split the initially loaded keyset [0, 1 billion) into disjoint sequential ranges
over the threads. Each thread continually overwrites each key in the range
continuously for 12 hours. When it gets to the end of it's range it returns
to the start.

Verification: at the end of the test we verify that every key in the [0, 1 billion)
range is present. We actually use ListObjectVersions to ensure that the
PutObject actually overwrote the "null" version and didn't introduce a
version of the object.

## Test5: PutObject Overwrite Versioned (05-run-put-object-overwrite-versioned)

This test enables versioning on the bucket.

We use 32 workers each with 128 threads. The benchmark runs for 12 hours.
We pick a contiguous 1 million key in the intially loaded 1 billion objects.
We split the range across all of the workers and threads. Each thread then
Each thread takes a key contiguous slice of the initally loaded 1 billion objects
and overwrites them continuously.

Verifcation: we keep a count of how many times each object was overwriten.
We then do a ListObjectVersions over the key-range and check that each object
has the expected number of version. The check only counts versions whose
timestamp is at or after the benchmark start time.

## Test6: Delete Multi (06-run-delete-multi)

This test delete all of the initially loaded 1 billion keys. We use 32 workers
each with 16 threads. The [0, 1 billion) key range is sharded into disjoint ranges over
the threads. Each thread issues delete multi requests with a page size of 1000
for sequential keys. We issue non-versioned deletes. The tests finishes when all
keys have been deleted for we exceed 12 hours.

Verification: we run list objects over each threads deleted range and assert
the keys do not exist.
